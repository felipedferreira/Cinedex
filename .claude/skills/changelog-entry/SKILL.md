# Add a Cinedex changelog entry (no release)

Records an unreleased change in Cinedex's [Keep a Changelog](https://keepachangelog.com)
changelog. The catch is that the changelog exists in **three** places that must
end up consistent, and only one of them is edited by hand — get the wrong one and
CI fails or the served changelog page goes stale.

The three copies:

| File | Tracked in git? | Who writes it | You touch it? |
|------|-----------------|---------------|---------------|
| `CHANGELOG.md` (repo root) | yes | **you, by hand** | **YES — the only one** |
| `backend/CHANGELOG.md` | yes | the backend build | never by hand — build + commit it |
| `backend/src/Presentation/Cinedex.WebService/wwwroot/CHANGELOG.md` | no (git-ignored) | the backend build | never — build artifact, regenerated |

CI runs a changelog-sync check that **fails if root `CHANGELOG.md` and
`backend/CHANGELOG.md` differ**. The `wwwroot` copy is the changelog page the web
service serves at `/movies-svc/CHANGELOG.md`; it is git-ignored, so it is never
committed — running the build just keeps the locally-served copy current.

## Workflow

Create a todo per step so nothing is skipped.

### 1. Edit ONLY the root `CHANGELOG.md`

Open [`CHANGELOG.md`](../../../CHANGELOG.md) at the repo root. Never edit
`backend/CHANGELOG.md` or the `wwwroot` copy — those are regenerated by the build
in step 2 and hand-edits to them will be overwritten and/or fail CI.

Add the entry under the existing **`## [Unreleased]`** heading (top of the file).
Do **not** create a new `## [x.y.z]` dated section — that is cutting a release,
which is a separate decision handled by the `release-version` skill. If the user
is asking to release, stop and use that skill instead.

Group the entry under the right Keep a Changelog category, creating the `###`
subheading under `## [Unreleased]` if it doesn't exist yet. Order categories
Added → Changed → Deprecated → Removed → Fixed → Security.

| Category | Use for |
|----------|---------|
| `### Added` | a new feature, endpoint, project, or capability that didn't exist |
| `### Changed` | different behavior of something that already shipped |
| `### Deprecated` | still works but slated for removal |
| `### Removed` | a capability/endpoint that's now gone |
| `### Fixed` | a bug fix |
| `### Security` | a vulnerability fix or hardening |

When a change both adds a capability and alters shipped behavior (e.g. swapping a
placeholder for a real implementation), pick by the **primary user-facing effect** —
a capability that now works where it didn't is `Added`; a tweak to how an existing,
working feature behaves is `Changed`. If it's genuinely a toss-up, ask the user.

**Match the house style** of existing entries (read a few first): a bold lead-in
naming the thing, an em-dash, then prose. Reference real type/route/project names
(remember the catalog entity is `Title` and the API base is `/movies-svc`, per
`ApiConstants.cs`). Where an entry closes a "known gap" called out in an earlier
release, say so.

```markdown
## [Unreleased]

### Added
- **Thing you added (`CodeIdentifier`)** - One or two sentences of prose describing
  what it does and why, in the voice of the surrounding entries.
```

### 2. Sync the generated copies via the backend build

The changelog copies are refreshed by the `BuildFrontend` MSBuild target in
`Cinedex.WebService.csproj`, which runs on any backend build. Run the full build
of the solution from `backend/`:

```bash
cd backend
dotnet build          # builds Cinedex.slnx; BuildFrontend refreshes both copies
```

This does three things in order: rebuilds the Vite landing/changelog pages into
`wwwroot`, copies root `CHANGELOG.md` → `backend/CHANGELOG.md`, then copies that
into `wwwroot/CHANGELOG.md`. After it, both generated copies reflect your edit.

- **Fresh clone / no frontend toolchain yet:** run `npm ci` once in
  `backend/src/Presentation/Cinedex.WebService/` first (the Vite step needs it).
- **Only need the changelog synced, not the landing pages** (e.g. Vite/npm not set
  up and you don't want to deal with it): `dotnet build -p:SkipFrontendBuild=true`
  still copies both changelog files — only the Vite page rebuild is skipped. Prefer
  the plain `dotnet build` when the toolchain is available so `wwwroot` is fully current.

### 3. Verify the sync, then commit both tracked files

Confirm root and backend copies are now identical (this is exactly what CI checks).
**From the repo root:**

```bash
git diff --no-index -- CHANGELOG.md backend/CHANGELOG.md   # expect no output
```

No diff = synced. Then stage **both** tracked files together:

```bash
git add CHANGELOG.md backend/CHANGELOG.md
```

Do **not** `git add` the `wwwroot` copy — it's git-ignored on purpose. Do not bump
any version numbers (`backend/Directory.Build.props`, frontend `package.json`) —
this skill adds an unreleased entry, it does not release.

## Guardrails / red flags

- **Editing `backend/CHANGELOG.md` by hand** → STOP. Edit root `CHANGELOG.md`, then
  let the build regenerate the backend copy. Hand edits get overwritten or fail CI.
- **Creating a `## [x.y.z]` dated section** → that's a release, not an entry. Use the
  `release-version` skill.
- **Committing without building** → root and `backend/CHANGELOG.md` drift and CI's
  changelog-sync check fails. Always build + verify before committing.
- **Trying to commit the `wwwroot` copy** → it's git-ignored; leave it as a build
  artifact.
- **Bumping the version** → not part of adding an entry. Leave `## [Unreleased]` as
  the heading.

## Relationship to `release-version`

This skill: add an entry under `## [Unreleased]`, no version change.
`release-version` skill: turn the accumulated `## [Unreleased]` entries into a dated
`## [x.y.z]` section and bump the version everywhere. Entries land here first;
releases happen later.
